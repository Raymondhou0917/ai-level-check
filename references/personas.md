# AI 使用人物志：16 型

> **先講最重要的一句：分型是風格，不是分數。**
>
> `QAOC` 不比 `PVSE` 差。一個把 AI 當隨手工具的人，和一個把 AI 接成生產線的人，
> 只是把 AI 用在不同的地方。等級（LV0–LV5）回答「已展現到什麼程度」，
> 分型回答「習慣怎麼用」。兩者不可換算，也不可相加。
>
> 報告裡出現分型的地方，都要把這句話一起寫上去。

---

## 四個軸

每一軸都要能從紀錄裡指出證據。指不出來就用 `?`，例如 `P?SE`。

### 軸一　交辦：**P** 給足脈絡 ↔ **Q** 先問再說

看**第一次交辦**時帶了什麼。

| 傾向 P 的訊號 | 傾向 Q 的訊號 |
| :-- | :-- |
| 首次發言就帶背景、範圍、限制或完成標準 | 先丟一句話問，靠後續補 |
| `behaviour_signals.spec_turns` 佔本人發言比例偏高 | 該比例偏低，但多輪對話數偏高 |
| 案例裡看得到「不要做什麼」「什麼算完成」 | 案例裡看得到「先看看」「你覺得呢」 |

**不看提示詞長度。** 一句話講清楚條件的人是 P，寫五百字廢話的人不是。

### 軸二　查核：**V** 動手驗證 ↔ **A** 直接採用

看查核有沒有**真的執行**，不是有沒有嘴上說。

| 傾向 V 的訊號 | 傾向 A 的訊號 |
| :-- | :-- |
| `verify_commands` 有實際的測試、diff、lint、build | 幾乎沒有查核類指令 |
| 案例裡有「跑起來看看」「這個數字哪來的」 | 產出後直接進下一題 |
| 有 WebSearch／WebFetch 去對來源 | 不查來源 |

A 不等於粗心。任務本身不需要查核時，不查核不是弱點——
這一點在報告裡要寫明，不要讓 A 被讀成負面。

### 軸三　沉澱：**S** 固化資產 ↔ **O** 一次性

看做完之後**有沒有留下下次能用的東西**。

| 傾向 S 的訊號 | 傾向 O 的訊號 |
| :-- | :-- |
| `artifacts.durable_writes` 有 SKILL.md、scripts/、workflows/、設定檔 | 產出集中在一次性文件 |
| `automation_evidence.sessions` 大於零 | 沒有自動化紀錄 |
| 同一套做法在不同案例重複出現 | 每次都從頭講一遍 |

### 軸四　動手：**E** 讓 AI 執行 ↔ **C** 只對話

看工具呼叫的**種類**，不是次數。

| 傾向 E 的訊號 | 傾向 C 的訊號 |
| :-- | :-- |
| 有 Bash／Edit／Write／瀏覽器／MCP 這類會改變世界的工具 | 幾乎只有文字往返 |
| `human_usage.unique_tools` 涵蓋執行類工具 | 工具集中在讀取與搜尋 |

C 型常見於行銷、企劃、客服、寫作場景，那裡本來就不需要讓 AI 動手改檔案。
**不要把 C 讀成能力低。**

## 16 型型錄

每型固定四欄：一句話、典型行為、常見盲點、下一步先做什麼。
「下一步」只挑最先需要的一個動作，且必須能融入日常工作，不新增行政任務。

### PVSE　系統建築師

- **一句話**：交辦前先想清楚，做完會留下一套別人也能跑的東西。
- **典型行為**：首次交辦就帶完成標準，過程實際驗證，結束後把做法寫成 Skill 或腳本。
- **常見盲點**：容易把不需要系統化的小事也系統化，維護成本堆在自己身上。
- **下一步**：挑一個已固化的流程，補上「維護人、版本、驗收條件、出錯找誰」四欄。

### PVSC　流程設計者

- **一句話**：想得清楚也寫得下來，但很少讓 AI 真的動手。
- **典型行為**：把方法論、SOP、模板寫得很完整，執行仍靠人。
- **常見盲點**：文件與實際執行脫節，寫下來的流程沒被跑過。
- **下一步**：挑一份自己寫的流程，讓 AI 只照文件跑一次，看它卡在哪。

### PVOE　精準特工

- **一句話**：每一次都交辦得很準、驗得很仔細，但做完就散了。
- **典型行為**：條件清楚、實際驗證、成果可用，卻沒沉澱成模板。
- **常見盲點**：同一件事重複交辦，每次都在重講一樣的背景。
- **下一步**：找出最近重複三次以上的交辦，把共同的前提寫成一段可貼的固定開頭。

### PVOC　求證派

- **一句話**：問得清楚、查得仔細，把 AI 當成需要交叉驗證的顧問。
- **典型行為**：追問來源、比對說法、要求依據，很少讓 AI 執行。
- **常見盲點**：驗證成本高，容易卡在「還不夠確定」而遲遲不動手。
- **下一步**：對其中一個已驗證過的結論，直接讓 AI 產出下一步的實際成果。

### PASE　自動化狂人

- **一句話**：很會設計流程、也很敢讓 AI 跑，但驗收這關常常跳過。
- **典型行為**：排程、hooks、agent 一大堆，出事才發現跑錯很久了。
- **常見盲點**：自動化沒有失敗處理，資料錯了照樣硬做出結果。
- **下一步**：挑一個排程，餵它一份缺資料的測試案例，看它會不會停下來回報。

### PASC　交辦型主管

- **一句話**：把要求說得很完整，然後就相信結果。
- **典型行為**：規格寫得好、模板做得好，收到成果直接採用。
- **常見盲點**：AI 的錯誤被規格的完整性掩蓋，錯了不容易被發現。
- **下一步**：對下一份交付，指定一個「必須自己核對」的欄位，例如數字或來源。

### PAOE　效率外包客

- **一句話**：交辦清楚、讓 AI 動手、拿到就用，速度是最高優先。
- **典型行為**：任務一次過，很少回頭改，也很少留下紀錄。
- **常見盲點**：小錯累積在沒人看的地方，出事時追不回當時的判斷。
- **下一步**：在最常做的那類任務加一行驗收句：「做完先告訴我哪裡你不確定。」

### PAOC　需求規格官

- **一句話**：擅長把需求寫清楚，剩下交給別人或別的工具。
- **典型行為**：產出多為文件、需求、大綱，AI 是打字與整理的加速器。
- **常見盲點**：規格與實作之間沒有人接住，寫完就停在那。
- **下一步**：把最近一份規格丟給 AI，請它指出「照這份做，最可能卡在哪」。

### QVSE　邊做邊修的工程腦

- **一句話**：先動手再說，但每一步都驗，也會把踩過的坑寫下來。
- **典型行為**：短提問、大量迭代、頻繁測試，最後沉澱成腳本或筆記。
- **常見盲點**：迭代次數換來的成果，別人看不懂那條路怎麼走出來的。
- **下一步**：在下次沉澱時，多寫一段「為什麼不是另一個做法」。

### QVSC　好奇查證家

- **一句話**：問題很多、查得很細，會整理成筆記，但不太讓 AI 動手。
- **典型行為**：探索式對話、追問來源、產出知識文件。
- **常見盲點**：知識累積得快，實際產出跟不上。
- **下一步**：挑一則整理得最好的筆記，直接改寫成一份可執行的檢核清單。

### QVOE　直覺實驗家

- **一句話**：想到就試，試完就驗，驗完就丟。
- **典型行為**：大量短任務、實際跑起來看、很少留下東西。
- **常見盲點**：好用的做法沒被記住，下次又從零開始試。
- **下一步**：把這期間最好用的那一次對話，原封不動存成一份範本檔。

### QVOC　抬槓辯論家

- **一句話**：把 AI 當對手，用來槓出自己的想法。
- **典型行為**：短提問、反覆質疑、不接受第一個答案，成果留在腦子裡。
- **常見盲點**：想清楚了但沒有落地，隔一陣子又要重新想一次。
- **下一步**：在下一次槓完之後，請 AI 用三行寫下「我們最後同意了什麼」，存起來。

### QASE　一把梭

- **一句話**：想到就丟，丟了就讓它跑，跑完拿來用。
- **典型行為**：短指令直接觸發執行類工具，速度極快，也真的做出東西。
- **常見盲點**：這是四個軸裡風險最高的組合——沒條件、沒查核、直接動手。
  一旦 AI 誤解需求，錯誤會直接寫進真實檔案或對外系統。
- **下一步**：對會動到真實資料的任務加一句「先給我看你要改什麼，我說好再動」。

### QASC　靈感速記員

- **一句話**：想到什麼就問什麼，AI 是隨身的第二個腦袋。
- **典型行為**：大量短對話、跨主題、即用即丟。
- **常見盲點**：好想法散在幾百則對話裡，找不回來。
- **下一步**：固定每週挑三則自己覺得有用的對話，貼進同一個檔案。

### QAOE　許願池

- **一句話**：許個願，看 AI 生出什麼，行就用。
- **典型行為**：一句話任務、讓 AI 動手、結果直接採用。
- **常見盲點**：成果好不好取決於運氣；AI 猜錯了也不容易發現。
- **下一步**：許願之後加一句「你打算怎麼做？先講不要動手」，只多花一輪。

### QAOC　閒聊夥伴

- **一句話**：把 AI 當聊天對象，問問題、聊想法、找靈感。
- **典型行為**：日常短問答、生活與工作混雜、不留紀錄。
- **常見盲點**：沒有盲點——除非工作本來需要準確度，那就會有。
- **下一步**：挑一件最近重複問過的事，請 AI 幫你寫成一段固定的問法。

## 使用規則

1. **一定要附證據。** 每個軸都要寫「判給這一端，是因為案例 N 的哪個行為」。
2. **資料不足就寫 `?`。** 例如 `PV?E`，並說明缺哪一種紀錄。
   不要為了湊出一個完整代號而硬判。
3. **不要把分型換算成等級。** 一個 `QAOC` 可能是 LV3，一個 `PVSE` 也可能只到 LV2。
4. **不要跨人比較。** 這份專案禁止排名、百分位與「勝過多少比例的人」。
5. **分型會變。** 同一個人在不同任務、不同季度會落在不同型。
   報告要寫清楚這是「本期間、這批紀錄」的分型，不是人格標籤。
6. 盲點欄位是**這一型常見的風險**，不是斷定這個人有這個問題。
   要寫進報告的不足，仍然必須有本人案例支持。

## 給團隊帶工作坊用

分型最好的用法不是貼標籤，是**讓一群人看見彼此的差異**：

- 同一個團隊裡，把 16 型畫成四個軸的分布圖，看團隊整體偏向哪裡。
  全隊都是 `A`（不查核）比任何一個人的等級都值得處理。
- 兩個人做同一類工作卻落在完全不同型，通常代表流程沒有共識，而不是誰做錯了。
- 分型可以公開，**等級與弱點不建議公開**。前者是話題，後者是個人資料。
