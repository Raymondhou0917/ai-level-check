# 證據與判斷規則

一份能力報告最容易壞掉的地方不是分析不夠深，是**把不同來源的東西當成同一種證據**：
把 AI 自己補上的條件算成本人的能力，把沒讀到算成沒做過，把單次事件寫成長期習慣。

這份文件就是為了擋住這幾件事。

---

## 資料範圍與隱私

1. 來源、期間與限制，統一在報告開頭的「參考資料範圍」交代一次，後文只補影響判斷的部分。
2. 只處理與工作或事業相關的內容。排除私人生活與客戶機密；
   混合內容無法安全分離時直接略過，**不提及也不暗示**被排除的內容。
3. 不推測整體使用頻率、用途百分比、節省時間或實際成效。
   期間內**掃到的**對話則數、本人發言次數與（有紀錄時的）token 可以列在報告上，
   必須附工作量備註，不得換成能力分數或「用得夠不夠勤」。
   本人自己估的數字要標成「自述」。

完整的同意、保存與使用邊界見 [privacy.md](privacy.md)。

## 證據歸屬

每個判斷都要指得出來自哪一類證據：

| 類別 | 是什麼 |
| :-- | :-- |
| **自建依據** | 本人建立且實際沿用的制度、流程、模板，或經確認的範例 |
| **本人陳述** | 本人對做法、理由或結果的說明 |
| **問答行為** | 本人實際提出的條件、判斷、追問與修正 |
| **工作行為** | 可歸屬於本人的成果、回寫、交接或複核紀錄 |
| **合理推論** | 由證據提出、尚待確認的解釋 |
| **AI 表現** | AI 提出的內容、查找結果與執行動作 |

四條硬規則：

1. **AI 自行補上條件、找到文件或完成流程，不算本人的能力。**
   本人沒回覆或沒反對，也不代表已理解、採納或完成。
2. 這份 skill、現成模板、模板裡預先寫好的要求，**不是本人能力的直接證據**。
   本人怎麼調整、運用與查核模板，才可以依實際案例分析。
3. 先前 AI 生成的能力報告不能取代原始證據。記憶可以當查找線索，無法核對時要標明。
4. 案例統一寫成「案例 N：工作短名稱」，沿用 `cases.md` 的編號。
   每個主要判斷附對應案例；首次完整說明時附簡短問答摘錄或去識別化摘要。
   後文沿用同一編號，不重複展開，**也不把同一事件當成多個發現**。

## 公平判斷

1. 評估**目前資料展現的**能力與行為，不推論整體工作能力、人格、態度或適任性，
   不生成排名，不做自動化決定。
2. **不以提示詞長度、對話輪數、專業術語、工具數量、訊息數或 token 評估能力。**
   簡短提問或沒用某個工具，本身不是弱點。
   訊息少有時代表 skill／harness 夠完整，有時只是這段期間用得少——報告可以列數字，不能當分數。
3. 依任務需要判斷，考慮前文已提供的條件。
   不要求每個簡單任務都包含完整背景、拆解、查核與流程設計。
4. 評估當時的行為，以**當時**已知資訊、可取得資料與適用規則為準，
   不用後來才有的做法反推本人先前做錯。
5. **未觀察到不等於不會**；找不到成果紀錄不等於沒完成。
   只有問答紀錄時，可以判斷問答行為，不推論沒被記錄的實際執行。
6. 發現問題時，一併檢查個人理解、AI 回答、權限、工具、自建文件、
   客戶與外包協作條件。原因可能並存，不強迫歸成單一責任。
7. 單人工作不因為缺少同事複核就直接算弱點；
   改看有沒有建立替代的查核方式（自我複核清單、AI 交叉檢查、事後驗收）。
8. **本人操作與自動化執行必須分開評估。**
   本人寫的 bot 或排程跑出來的對話，不是他的提問行為；
   把兩者混在一起算，會同時弄壞提問分析與自動化分析。

## 四種判定量表

四把尺量四件不同的事，**不可互相換算，不可加總成一個分數**。

### 能力程度：目前做到什麼程度

| 級別 | 判準 |
| :-- | :-- |
| **系統等級** | 已有實際案例支持任務分工、例外處理、驗證、交接與複用。不能只憑提出設計構想 |
| **穩定運用** | 多個獨立案例顯示能提供必要條件、有效修正並進行適當檢查 |
| **基礎使用** | 有案例顯示能推進或完成單次任務，但在該任務需要的條件設定、修正或檢查上仍有限 |
| **尚未觀察** | 證據不足，不評定高低 |

能力程度與弱點分開呈現。**即使某項能力達到穩定或系統運用，仍可能存在重要不足。**

### 穩定程度：出現幾次、是否持續

| 級別 | 判準 |
| :-- | :-- |
| **明確習慣** | 跨時間、跨案例有一致且可追溯的證據 |
| **多次出現** | 不同事件重複出現，但觀察範圍有限 |
| **單次出現** | 一個獨立事件支持 |
| **資料不足** | 不能判斷是否穩定 |

同一事件的多輪對話**不算**多個案例。

### 問題分類：這個不足有多確定

| 級別 | 判準 |
| :-- | :-- |
| **確認不足** | 該任務確實需要，本人當時也有資訊或條件處理，但直接證據顯示做法遺漏、錯誤或無法推進任務 |
| **疑似不足** | 有問題跡象，但重要的替代解釋尚未排除 |
| **尚未觀察** | 資料不足，不列為弱點，也不列為通過 |
| **外部限制** | 有證據顯示主要阻礙來自資料、權限、工具、平台規則或客戶條件，不直接算個人不足 |

單次事件足以指出「這次做法的問題」，不足以認定為長期習慣。
但**高影響的單次問題不可省略**。

### 證據強度：這個判斷有多少依據

| 級別 | 判準 |
| :-- | :-- |
| **高** | 直接證據充分，脈絡清楚，重要替代解釋已檢查 |
| **中** | 有具體證據，但脈絡不完整或仍有未排除的解釋 |
| **低** | 主要靠片段、自述或間接線索，只能提出待確認的觀察 |

證據強度表示**判斷的確定程度，不是能力分數**。
單次事件也可能有高強度證據，但仍然只支持單次判斷。

## 改善優先級

| 級別 | 判準 |
| :-- | :-- |
| **優先處理** | 可能造成重要事實錯誤、不當承諾、資料處理風險或重大返工 |
| **持續改善** | 已反覆影響任務品質、問題釐清或交付 |
| **建議練習** | 影響有限、已有替代做法的局部不足 |

已觀察到的影響與尚未發生的可能影響要分開標示。
**優先級不能取代證據強度。**

## 七項核心能力

分析 AI 使用能力時，逐項檢查這七項：

1. **目標說明與任務拆解**：有沒有說清楚目的、完成標準及相互依賴的步驟
2. **能力邊界**：有沒有辨識 AI、查證與人工判斷的界線
3. **背景資料**：有沒有提供或引導查找會改變答案的重要資料與限制
4. **問答迭代**：有沒有指出具體問題，讓下一輪修正確實解決問題
5. **品質控制**：有沒有適當查核事實、來源、數字、假設、矛盾與遺漏
6. **工具運用**：有沒有選用符合任務需要的方法，避免可觀察的資料缺漏與錯誤
7. **流程整合**：有複用或交接需求時，有沒有形成可理解、可複核、可複用的成果

**不要只因為本人沒明說「請查核」就判定沒有查核。**
要看完整的可見脈絡與後續採納行為。

## 工作系統與組織強度

這是原版 Prompt 的 B 節，報告第 4 節必須寫，不能用多棲圖或齒輪格子代替。

從問答找出最多三個代表性工作主題，對照本人的自建文件與實際營運資料，觀察：

- 是否理解該工作的目的、限制與完成要求
- 是否使用或要求查找適用資料
- 是否辨識哪些環節需要外部資料、專業意見或事後複核
- 是否考慮成果存放、版本，以及「未來的自己或接手者」如何接手
- 是否辨識並修正不符合自身營運情境的 AI 建議
- 涉及方案取捨時，是否提出呼應自身定位、服務理念或設計原則的理由

組織強度的判斷標準：同一件事，傳統公司會要求的明確目的、驗收條件、例外處理與交接文件，本人的做法是否具備**等效機制**。有等效機制即成立，不要求形式上模仿公司文件。

只有自建文件或實際紀錄明確支持時，才能判斷是否符合本人自訂的標準。網路上的通用做法、單一案例或未確認草稿，不直接視為本人的標準。

文件矛盾、過期或適用性不明時，標示對照依據不足。能辨識例外、質疑不適用流程或提出有依據的改善，也是理解的證據，不以「有沒有照慣例做」判定理解程度。

分開呈現這三層，不互相替代：

1. 能說明原則
2. 能解釋情境取捨
3. 已有實作證據

無法讀取必要來源時，明確標示未完成交叉對照，不用通用職場常識代替。

## AI 對本人事業背景的掌握

這是原版 Prompt 的 C 節。評的是**對話裡那位 AI**，不是本人的能力，必須獨立成段，不要混進第 4 節的對照表。

檢查可見案例中的 AI 是否：

- 實際讀取適用的自建文件與工作資料
- 正確運用本人的定位、專案脈絡與工作要求
- 辨識資料缺口、規則衝突，以及需要人工判斷之處

不因 AI 回答提到本人的事業名稱就認定它理解該事業。
不以目前取得的資料推定過去已取得。
不把單次表現當成永久掌握。

沒讀到自建文件或事業資料時，寫「尚未觀察」並說明缺哪種來源，整塊仍要出現，不能省略。

## 應用成熟度

這是原版 Prompt 的 D 節，用在報告第 5 節「目前怎麼用／以後可以怎麼用」。
最多選三個實際任務，分開標示**目前**與**潛在**成熟度。

| 名稱 | 意思 |
| :-- | :-- |
| **一次性用法** | 偏個人偏好或單次需求，用完即止 |
| **日常輔助** | 反覆協助本人工作，但做法只存在本人腦中或散落對話裡 |
| **可複用資產** | 已固化為模板、指示頁或方法，未來的自己、外包者或協作者可直接使用 |
| **制度化流程** | 有固定觸發、明確資料來源、驗收條件與維護機制，具公司級組織強度 |

成熟度不代表能力高低，也不可換成 LV。判斷時看：複用需求、標準化條件、錯誤影響、檢查責任、維護成本。缺少條件時保留未知，**不把所有用法推向制度化**。

報告輸出一律寫等級全名，不單獨使用 A–D 代號，也不用「已經在用」代替成熟度名稱。

## 報告用語

1. 用新手能一次看懂的日常用語，寫清楚誰、何時、做了什麼。
   短句要保留完整意思，避免抽象名詞與空泛稱讚。
2. 全文不輸出 Markdown 粗體或斜體符號；標籤寫成「標籤：內文」。
   用標題、表格或條列呈現層次。表格太寬就改成逐項條列並保留欄位名稱。
3. 填高／中／低時加一句原因；填「尚未觀察」時說明缺少哪一種紀錄。
   「已理解哪些要求」要列具體要求與支持該判斷的行為，不能只填「良好」。
4. 改善建議統一講清楚：**誰在下一次同類工作中，對哪份資料或哪個流程做什麼，
   以及什麼結果才算完成。** 只提有證據支持、可融入日常工作的動作。
   「加強查核」「多練習」不能單獨成為建議。
5. 分清已完成的做法、未來建議與未實測的項目。未來用法要寫清楚成立條件，
   不能冒充現有能力；未實測不等於失敗。

## 交付檢查

1. **證據**：每個優點與不足都有依據，採同一套標準。
   沒有為了填滿格式、配合期待或維持正面語氣而捏造或淡化問題。
   資料量不當成能力高低，不計算缺乏驗證基礎的個人總分。
2. **判斷**：已確認的不足直接指出，不用稱讚包裝；
   未知仍保留未知，**不改寫成「仍有成長空間」**。
   個人、AI 與外部限制三種原因分開，不互相掩蓋。
3. **改善**：每項不足都有情境、影響與下一次可做的動作；提不出建議時說明原因。
   只檢驗有沒有等效做法，不要求個人模仿公司文件形式。
4. **閱讀**：欄位與句子意思完整、案例編號一致；
   刪掉重複說明、一般性教學與沒有依據的新結論。
