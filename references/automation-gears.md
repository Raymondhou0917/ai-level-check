# 自動化齒輪：五種讓事情自己發生的機制

一個人會不會用 AI，最後會落到一個問題上：**他離開鍵盤之後，還有沒有事情在發生？**

但「有沒有做自動化」問得太籠統，答案永遠是「有啊我有用」。
這份文件把它拆成五顆具體的齒輪——因為現代系統要讓一件事自己發生，
底層就只有這五種扳機。

分類來自雷蒙三十《超級 AI 個體》課程附錄〈驅動 AI 的 5 種永恆齒輪〉。

---

## 五顆齒輪

```
你要讓什麼事自己發生？
│
├─►「每天特定時間、每隔幾小時做一次」
│     └── ① 時間排程　Schedule / Cron / launchd
│
├─►「外部系統一有動靜（有人填表、刷卡、留言）就立刻處理」
│     └── ② 網路鉤子　Webhook / n8n
│
├─►「打開 AI、關掉對話、git commit 的那一瞬間，強制插隊做件事」
│     └── ③ 生命週期鉤子　SessionStart / pre-commit / pre-push
│
├─►「推上 GitHub 之後，雲端自動測試、打包、更新正式站」
│     └── ④ 持續整合部署　GitHub Actions / Zeabur / Vercel
│
└─►「常駐的機器人當掉要自動拉起來，死了要通知我」
      └── ⑤ 守護與心跳　pm2 / KeepAlive / healthcheck
```

---

## 為什麼把它放進評估

三個理由：

1. **LV4–LV5 本來就要求這個。** 「把有效做法固定成模板或代理」（LV4）、
   「整合成實際運作的工作系統」（LV5）——講的就是齒輪。
   齒輪只是把這兩級的門檻講成具體、查得到的東西，**不是新增的門檻**。
2. **它們全都在硬碟上留痕跡。** 寫了什麼檔、跑了什麼指令、用了什麼工具，
   證據包本來就有，不用額外蒐集，也不用受評者填任何表。
3. **它是共同語言。** 「你用過幾顆齒輪、哪幾顆」比「你會不會自動化」好談得多，
   帶團隊工作坊時尤其明顯。

---

## 三條不能越過的線

### 1. 覆蓋度不是分數

**五顆全用過不比兩顆好。** 一個內容工作者只需要 ① 和 ②，
硬去搞 ④ CI/CD 只是浪費時間。這份專案的規則寫得很清楚：
不要求沒有複用需求的工作為了升級而自動化。

報告裡出現覆蓋度的地方，都要寫上這句。

### 2. 沒用過某顆，不等於不會

齒輪是**期間快照**。這 14 天沒改到 hooks，不代表這個人沒有 hooks——
很可能是它三個月前就設好、一直穩定在跑，所以這期間根本不需要動它。

所以未觀察到的齒輪只能寫「本期間未觀察到」，**不能寫成弱點**。
要判斷「是不需要」還是「不會」，得看那個人的工作有沒有對應的複用需求——
這一題證據包答不了，只能由分析階段讀案例、或由本人自願校正。

### 3. 「做了」跟「提到」是兩件事

這是實作時踩到的坑，值得寫下來：

第一版偵測直接拿關鍵字掃所有指令字串，結果 5 顆全中——
但證據長這樣：

```
② 網路鉤子的證據：指令 `rg -n -i "facebook|instagram|webhook|messag…"`
```

那是在**搜尋** webhook，不是在**架** webhook。
更糟的是 `cat > collect.py <<'EOF' …整份程式碼…` 這種 heredoc，
內文會整段被掃進去誤中。

收緊之後同一批資料變成 3／5，每一顆都指得出真實的 artifact。
**一個會誤報的偵測器，比沒有偵測器更危險**，因為它產出的是看起來有根據的假證據。

## 偵測規則

每顆齒輪三種各自獨立的訊號，全都要求是「動作」：

| 訊號 | 是什麼 | 強度 |
| :-- | :-- | :-- |
| **寫檔** | 寫出了讓它發生的那個檔 | 最強 |
| **指令** | 跑了會改變系統狀態的動詞 | 強 |
| **工具** | 用了只能拿來建這件事的工具 | 強 |

指令一律先過 `cmd_action()`：在第一個 `<<` 切斷，只看 heredoc 前面那個動詞。

### 各齒輪的判準

| 齒輪 | 寫檔 | 指令 | 工具 |
| :-- | :-- | :-- | :-- |
| ① 時間排程 | `LaunchAgents/*.plist`、`crontab` | `crontab -e/-l`、`launchctl load/bootstrap`、`schtasks /create` | `CronCreate`、`ScheduleWakeup`、`scheduled-tasks` MCP |
| ② 網路鉤子 | 路徑含 `webhook`、`/api/hooks/`、`callback_url` | `ngrok http`、`n8n start`、`cloudflared tunnel` | `mcp__n8n*` |
| ③ 生命週期鉤子 | `.claude/settings*.json`、`.git/hooks/`、`/hooks/*.sh`、`pre-commit` | `git config core.hooksPath`、`pre-commit install`、`husky install` | — |
| ④ 持續整合部署 | `.github/workflows/*.yml`、`Dockerfile`、`zeabur.json` | `gh workflow run`、`vercel --prod`、`docker build/push` | `mcp__zeabur__deploy*`、`create-service` |
| ⑤ 守護與心跳 | 路徑含 `watchdog`、`heartbeat`、`healthcheck`、`keepalive` | `pm2 start/restart`、`supervisorctl start`、`systemctl restart` | `Monitor`、`firecrawl_monitor_create` |

**刻意不收的訊號**：`grep`／`rg`／`cat`／`find` 這類查詢指令、
heredoc 內文、只是路過提到關鍵字的檔名。寧可漏報，不要誤報。

## 怎麼用在報告裡

### 對 LV4 的意義

LV4 要求「把有效做法固定成模板、指示頁、Skill 或自動化代理」。
**至少一顆齒輪有實作證據**，是這句話的具體化——但它不是唯一路徑：
寫成一份被反覆使用的 SKILL.md 同樣算 LV4，不一定要有齒輪。

### 對 LV5 的意義

LV5 要求「整合成實際運作的工作系統」。實務上這通常意味著
**兩顆以上的齒輪咬合**，例如：

```
① Schedule 每天 08:30 觸發
   └─► 跑完把結果寫回檔案
       └─► ⑤ Watchdog 確認它今天有跑、沒跑就通知
```

但一樣不是硬門檻。單一顆齒輪如果本身就有分工、完成標準、例外處理與維護，
一樣可以支持 LV5；反過來，五顆齒輪各自為政、沒有一顆有錯誤處理，也到不了 LV5。

**齒輪回答「有沒有讓它自己跑」，四項系統驗證回答「跑得對不對」。**
兩件事分開判，不可互相替代。

### 報告要怎麼寫

- 列出本期間觀察到的齒輪，每顆附證據（寫檔路徑／指令／工具名）
- 未觀察到的齒輪寫「本期間未觀察到」，並說明無法判斷是不需要還是不會
- 同一區塊寫上「覆蓋度不是分數」
- **不要**畫成雷達圖或進度條——那會讓人以為五顆全滿是目標

## 給課程與工作坊

這一層特別適合帶學員：附錄教完五顆齒輪之後，讓他們跑一次檢核，
直接看到自己實際用了哪幾顆。

比起「你學會了嗎」，「你的硬碟上有沒有留下痕跡」是誠實得多的問題。

團隊層級最有價值的看法不是誰用得多，而是——
**全隊都沒有 ⑤ 的話，那代表所有自動化都沒有人在看它有沒有掛掉。**
那是團隊問題，不是個人問題。
